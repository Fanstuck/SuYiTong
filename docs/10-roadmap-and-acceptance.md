# 10 开发路线与验收标准

## 1. 路线原则

- 文档和评测先于完整开发。
- 先完成单条纵向闭环，再扩展全部角色和页面。
- 每阶段有独立交付和退出条件。
- 研究方法和产品平台分开验收。
- 不以“能生成文字”代替系统完成。

## 2. 阶段路线

### P0 文档与决策冻结

目标：确认做什么、为什么做、如何评测。

交付：

- 项目章程；
- 范围与需求；
- 主研究方向；
- 工作流和架构；
- 质量门与评测方案；
- 风险与开放问题；
- 比赛需求追踪矩阵（获得正式规则后补充）。

退出条件：高优先级开放问题已回答，文档状态从草案进入已冻结。

当前状态（2026-08-14）：文档基线已经完整形成，但比赛正式规则和主研究方向尚未冻结；允许 P1 技术验证并行推进。

### P1 JiuwenSwarm 技术验证

目标：验证 v0.2.2 的真实能力和二次开发边界。

交付：

- 本地可复现安装记录；
- 版本和配置清单；
- 单 Agent/Team/Skill/Tool/Memory smoke tests；
- 事件与 trace 样例；
- 最小 Fork 清单；
- 技术风险更新。

退出条件：核心能力可运行，或明确替代方案与限制。

当前状态（2026-08-14）：进行中。已完成 v0.2.2 锁定部署、Web 构建、轻量化渠道裁剪、四端口启动和 HTTP 冒烟验证；待完成真实模型调用、Agent/Team/Skill/Memory 专项验证。

### P2 研究证据纵向切片

目标：完成“研究题→文献→证据→Claim”的最小闭环。

实现：

- Project/Stage/Artifact 基础模型；
- Intake 与 Topic Approval；
- Literature Scout；
- OpenAlex/arXiv/Crossref 工具；
- Evidence Ledger；
- Claim Ledger；
- 基础 Web 页面或管理界面；
- 引用真实性质量门。

退出条件：一个真实 Agent 题目能够形成已验证文献和可追溯 Claim。

提前完成的基础项：速易通 API、Project 模型、阶段状态机和 SQLite 仓储已经建立；Literature/Evidence/Claim 尚未实现。

### P3 方法与实验闭环

目标：完成“假设→实验计划→真实运行→结果审计”。

实现：

- Methodologist 和 Experimenter；
- Experiment Plan schema；
- 实验沙箱、资源限制和日志；
- Metric schema 与统计工具；
- Result Audit；
- 实验质量门和人工审批。

退出条件：至少一组基线与消融可从干净环境运行并重建结果表。

### P4 论文与质量闭环

目标：从已批准 Claim 和结果生成合规论文交付。

实现：

- ICLR LaTeX 模板；
- Paper Writer；
- 多视角内部 Reviewer；
- 修订任务和版本差异；
- Q0—Q7 质量门；
- 匿名稿、署名稿和 delivery manifest。

退出条件：完整交付包通过所有阻断级规则。

### P5 研究评测与论文实验

目标：比较 PACM-SW 与基线，形成可发表实验结果。

实现：

- 任务集和数据划分；
- B0—B3 与 Ours；
- 固定 Prompt/模型/预算；
- 自动、人工和外部审稿评测；
- 消融、鲁棒性和成本分析；
- 统计脚本和表格重建。

退出条件：主表和主要图能够从原始运行记录重建，结论与结果一致。

### P6 稳定化与比赛演示

目标：提升稳定性、可解释性和演示完整度。

实现：

- 检查点恢复；
- 错误与超时治理；
- 权限和安全测试；
- 成本面板；
- 项目模板和演示数据；
- 一键构建交付包；
- 演示脚本与失败备用路径。

退出条件：在全新环境按文档能够完成一次端到端演示。

## 3. 依赖顺序

```text
文档冻结
  → JiuwenSwarm 技术验证
  → 项目/产物/状态基础
  → 文献与证据
  → 方法与实验
  → Claim 与论文
  → 质量门
  → 方法评测
  → 稳定化与演示
```

不建议先做完整 UI，也不建议先做“一键生成论文”页面。

## 4. Definition of Ready

开发一个功能前必须满足：

- 对应需求有编号；
- 输入、输出和错误已定义；
- 数据归属和权限明确；
- 质量与验收方法明确；
- 外部依赖和版本已确认；
- 不与已冻结决策冲突。

## 5. Definition of Done

功能完成必须满足：

- 代码和配置已版本化；
- 单元/集成测试通过；
- 结构化日志和错误信息完整；
- 权限策略验证；
- 文档同步更新；
- 可在干净环境复现；
- 对应质量门或验收脚本通过；
- 不依赖未记录的手工操作。

## 6. 端到端验收场景

### 场景 A：全流程 Agent 研究短论文

输入：Agent 记忆或上下文工程方向、6 页限制、给定模型和算力。

预期：完成选题审批、文献、方法、真实实验、Claim、ICLR 论文、质量门和交付包。

### 场景 B：已有实验结果的半流程论文

输入：研究问题、代码、数据说明和结果文件。

预期：验证实验产物，补齐证据和 Claim，生成论文并报告缺失的复现信息。

### 场景 C：已有论文审核

输入：英文 PDF/LaTeX。

预期：建立引用与 Claim 审核视图，运行内部 Review 和质量门，不虚构缺失实验。

### 场景 D：失败与恢复

输入：运行中制造工具超时或实验失败。

预期：记录失败、停止阶段推进、从检查点恢复，不丢失原始日志。

### 场景 E：权限阻断

输入：Agent 尝试删除项目数据、安装依赖或对外发布。

预期：按策略 ask/deny，并生成审计记录。

## 7. 项目交付物

进入完整开发后，仓库预计包含：

```text
apps/                  # API 与本地 Web
domain/                # 项目、状态、产物和审批模型
agents/                # Agent profiles
skills/                # 科研 Skills
tools/                 # 工具与 MCP 服务
memory/                # Context Pack 与研究图
quality/               # 规则引擎和 profiles
experiments/           # 实验执行与评测框架
templates/             # ICLR 等模板
infra/                 # 本地部署
tests/                 # 单元、集成、回放和 E2E
docs/                  # 项目文档
vendor/jiuwenswarm/    # 固定上游或子模块
```

目录仅为规划建议，待 P1 技术验证后冻结。

## 8. 时间与资源估算原则

当前不提供承诺式日期。获得以下信息后再做排期：

- 比赛准确截止日和强制功能；
- 可投入开发人数和角色；
- 可用模型、API 和算力；
- v0.2.2 本地验证结果；
- 任务集规模；
- UI 演示要求。

排期应包含技术验证、实验失败、文献核验和论文修订时间，不能只按编码工时估算。
